01

The short version

If I didn't know this was six weeks of solo AI-assisted work, I'd guess a small team over six months — and I'd assume they had no release engineer.

The Rust is the strongest part and it isn't close. Clippy is clean across the entire workspace, 609 tests pass, and there is not a single TODO or FIXME in the tree. The server has exactly three unwrap/expect calls and all three are provably unreachable. Blocking SQLite work is uniformly wrapped in spawn_blocking — the single most common way AI-written Axum code goes wrong, and it's right here everywhere.

The security work is not cargo-culted. Argon2id with per-password salts, a dummy-hash run on unknown usernames so login timing doesn't leak account existence, O_NOFOLLOW opens with symlink rejection on the asset path, digest re-verification on read, parameterized SQL with no injection surface I could find, CORS defaulting to same-origin, and scoped API tokens hashed at rest. Someone thought about attackers.

The documentation is also better than it has any right to be — an accuracy pass found 26 of 28 documented claims correct against the source, which is not what six-week docs usually look like.

Against that, the delivery pipeline is the weak half of the project, one specific thing is actively broken right now, and your repository currently states two incompatible licenses.

Fix this first

Your next v* tag push will fail. web/ does not type-check at HEAD — two errors in AttachmentLightbox.tsx:56, introduced 22 Aug by PR #82. No gate anywhere catches it: CI runs Biome and Vitest but never tsc, and your own check-pr.sh builds the docs site while skipping the product build.

Because npm run build only runs inside the tag-gated Docker and desktop jobs, the failure surfaces during a release — taking down the image build and all three installer builds at once. Last tag was 13 Aug, so it has been latent for nine days.

04

What the SaaS pivot actually costs

The headline is better than you probably expect. The schema is already multi-tenant. Every table carries account_id with ON DELETE CASCADE and composite indexes, and the read paths I traced validate ownership before querying by id. The single most expensive SaaS retrofit — bolting tenancy onto a single-user data model — is a problem you don't have.

Tenant isolation is enforced by threading auth.account_id into each query by hand. That's correct in the code I read, and the ownership-check-then-query pattern in list_conversation_source_stats is exactly right. But nothing structural stops one forgotten predicate, and the blast radius is one customer reading another's private messages. That deserves a dedicated test suite, not vigilance.

Carries over as-is

  • Multi-tenant schema with cascade deletes and per-account indexes
  • Scoped, revocable, hash-at-rest API tokens with expiry
  • Opaque session tokens — nothing forgeable if the DB leaks
  • Content-addressed assets, which makes object storage a clean swap
  • Resumable multipart upload already implemented
  • Real FTS5 search over body, subject, and attachment transcriptions

Needs real work

  • All writes serialize through one Mutex<Connection> — a hard concurrency ceiling
  • Every authenticated request runs schema DDL on a fresh connection
  • Rate limits are auth-only, in-memory, and reset on restart
  • Assets are local disk only — single node, needs a volume
  • SIGTERM is unhandled, so docker stop hard-kills mid-import
  • 167 eprintln! calls and no tracing, metrics, or error reporting
The one that will bite quietly

resolve_auth opens a new SQLite connection and runs ensure_accounts_schema on every authenticated request. It's invisible at single-user scale and becomes your throughput wall under real load. Schema-ensure already runs at startup, so the per-request call is pure waste — dropping it plus adding a connection pool is likely your highest-leverage performance change.

Frontend: disciplined, with two product-shaped holes

The TypeScript hygiene is better than most professional codebases: zero any in product code, zero @ts-ignore, zero non-null assertions, and hand-rolled fetch hooks that correctly use AbortController and refs to dodge stale closures. Biome runs with useExhaustiveDependencies at error level.

Two gaps are about the product rather than the code, and both show up worst on exactly the data this app is for — someone's decade-long thread with their mother.

Message threads render every message to the DOMHigh

The contacts list is properly virtualized, but the message thread isn't — it maps straight over the array. Year mode then loads an entire calendar year in sequential 500-message fetches. A busy year is 10k+ DOM nodes built on the main thread.

web/src/screens/message/MessageThread.tsx:39 · web/src/lib/useConversationMessages.ts:53-75
FixReuse the VirtualList you already built and proved for contacts.
Opening one conversation costs O(N) requestsHigh

There is no GET /v1/export/conversations/{id} endpoint — only the list and a /sources sub-route. So the client pages through the entire conversation list 100 at a time until it finds the id. For a vault with thousands of threads, opening one is dozens of round trips.

web/src/lib/fetchConversationById.ts:15-34 · 45 documented routes, no by-id
FixAdd the by-id endpoint. It's a small server change that removes an entire class of latency.
API responses are cast, never validatedMedium

return res.json() as Promise<T> — every endpoint, no runtime check. Types are hand-written mirrors of the server's. The desktop app and server version independently, so a renamed field doesn't throw; it silently renders wrong. There's also no error boundary anywhere, so a render crash is a white screen.

web/src/lib/api.ts:45 · no ErrorBoundary in tree
FixZod at the client edge, starting with conversations and messages. Add one top-level error boundary.
Session token in localStorage, no 401 handlingMedium

The token persists in localStorage and is validated once at startup. There is no 401 interception anywhere in the codebase — when the 30-day token expires mid-session, the UI degrades into scattered 401: error strings rather than redirecting to login.

web/src/lib/auth.tsx:48-92, 130-179
FixA global 401 → clear-and-redirect in the api client. Worth revisiting httpOnly cookies before hosting.

Documentation

This is the section where I expected to find AI-generated volume, and I didn't. A dedicated accuracy pass checked 28 documented claims against the source — 26 were correct. Env-var tables, rate-limit constants, search operators, import defaults, demo credentials, schema version, and every route in the API guide all match the code. Documented commands work as printed.

Two structural things deserve credit. The OpenAPI spec is generated by utoipa and guarded by a test — committed_openapi_matches_dump fails the build if the committed spec drifts from the routes. And the docs are willing to admit what doesn't exist: the Trash page says outright that restore and empty-trash routes "are not part of the current vault server. Treat Trash as a placeholder." That kind of honesty is rare and it's worth protecting.

The real gaps are trust-facing content and release history, not accuracy.

Your AI-steering files describe the wrong auth systemHigh

CLAUDE.md and AGENTS.md both say sessions are JWT. They aren't. Local sessions are opaque mv-user- random tokens, SHA-256 hashed at rest with a 30-day TTL; jsonwebtoken appears only to verify Hanko's RS256 tokens via JWKS. Your actual design is the better one — revocable, no signing secret, nothing forgeable from a DB leak.

This matters more than a normal doc bug: these two files prime every AI session on this repo. Two of my own audit passes inherited the error before I checked the source.

Nothing documents privacy, data handling, or backupHigh

This product ingests the most sensitive data a person owns, and there is no privacy policy, no data-retention statement, no telemetry disclosure, no threat model, and no TLS/reverse-proxy guidance for self-hosters. 08

Calibration

You asked for honesty, so here's the part that matters: the common failure mode of AI-assisted solo projects is not present here. That failure mode is impressive-looking breadth over a hollow core — plausible code that doesn't cohere, tests that assert nothing, and docs describing software that was never written. This isn't that.

The evidence against it is specific. 609 tests that genuinely exercise the HTTP layer against a real router on an ephemeral port. Zero clippy warnings across 82k lines of Rust. A hand-written FTS query parser with a golden-file corpus. Guest-isolation tests that go auth → handler → database. A generated API spec with a test that fails the build if it drifts. And when an independent pass checked 28 documented claims against the source, 26 were correct — the docs describe software that actually exists, which is precisely the thing that's usually false.

You also ran your own 65-finding Rust audit today, and its three "high" items are all documentation issues — no correctness or security findings. My independent pass agrees with that verdict, which is worth stating plainly: two separate audits went looking for something alarming in the Rust and neither found it.

The weaknesses cluster tightly, and it's a recognizable cluster: the things a solo developer has no colleague to be annoyed by. Nobody's release got broken by your merge, so nothing forced a build gate. Nobody had to page someone at 3am, so there's no structured logging. Nobody inherited an unfamiliar schema, so migrations stayed manual. Nobody's lawyer asked which license applied, so two answers coexisted. Every one of those is cheap now and expensive once customers exist.

Concretely: the seven items in section 03 are roughly two focused days. That work converts this from "impressive personal project" to "defensible commercial foundation," and none of it requires touching the architecture — which is the real compliment here.

The one genuine architectural decision still ahead is the write path. A single mutex over one SQLite connection is correct and honest for self-hosting, and it is a ceiling for multi-tenant hosting. You don't have to solve it before launch, but decide deliberately whether the hosted tier is per-tenant SQLite files (which suits your content-addressed, cascade-scoped design remarkably well) or a shared Postgres — because that choice gets much more expensive after the first hundred customers.
